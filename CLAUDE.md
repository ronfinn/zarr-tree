# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`zarr-tree` is a small, fast, read-only Rust CLI for inspecting Zarr, OME-Zarr
and SpatialData structure and metadata — in a local directory, under an S3 key
prefix, or on an HTTP server — without ever reading array or chunk data.

It is a personal project with one developer, who is also its main user. Keep
process proportionate to that.

Layout is deliberately flat: `src/main.rs` holds the whole program plus its unit
tests, and `tests/cli.rs` holds integration tests that run the compiled binary
against throwaway fixture stores.

## Workflow

- Work directly on `master`. No feature branches, pull requests, issues or
  release branches are needed for normal work.
- One small, understandable change per commit, with a `feat:` / `fix:` /
  `docs:` / `test:` / `chore:` prefix, an imperative summary and a short
  paragraph on why.
- Update tests and the affected docs in the same commit —
  `docs/status.md` when a capability changes, `CHANGELOG.md` for anything a
  user would notice.
- Run the quality gate below before every commit. CI runs the formatting,
  Clippy, test and MSRV checks on every push.
- Never force-push `master`. Release tags are immutable; never move or re-cut
  one.
- Releasing is a version bump in `Cargo.toml`, a dated `CHANGELOG.md` heading,
  a commit and a tag. Only when asked.

## Quality gate

```sh
cargo fmt --check
cargo check
cargo clippy --all-targets -- -D warnings
cargo test
cargo +1.88.0 check --locked
git diff --check
```

Useful variants: `cargo test <name>` to substring-match, `cargo test <name> -- --exact`
for exactly one, `cargo test -- --nocapture` to see printed output.

## Design rules

These are what the implementation rests on. Keep them true.

- **Read-only and metadata-only.** Nothing is opened for writing. No chunk,
  pixel, Parquet record or AnnData value is ever read.
- **Arrays are leaves**, locally and remotely: traversal stops at an array and
  its chunk objects are never listed. This is what makes a remote walk
  affordable.
- **Inspection, not validation.** The default output checks nothing against a
  specification. Values are printed as stored, and no default is invented for
  a missing key. `--validate` is the one exception, and it checks structure a
  store declares against the store itself — never a document against a schema.
- **Recognition comes from metadata markers**, never from directory names.
- **Graceful degradation.** An unreadable field prints `?`, an unreadable node
  prints `[unknown]`, and the rest of the walk continues.
- **Storage-neutral.** Traversal, interpretation and both renderers know
  nothing about where bytes come from; only the `Store` trait and its
  implementations do. `read`, `children` and `check_root` are the Zarr walk;
  `files` and `read_suffix` exist for binary payloads, and `read_suffix` can
  only ask for the end of an object.
- **A GET-only HTTP server is "unable to list", never "missing".**
  `RemoteStore`'s `reachable` flag exists to make that distinction provable.
- **Consolidated metadata is an overlay `Store`**: opportunistic (nothing that
  worked without it may depend on it) and all-or-nothing (a tree is never half
  snapshot, half live). Only `files` and `read_suffix` reach the physical
  store beneath it.
- **Validation is seven rules over metadata already read**, in a
  `Vec<ValidationFinding>` — no rule type, registry or engine. `WARN` means
  "could not check", never "broken". `--validate` is refused with `--depth`.
- **Exit status** 0 walked (or validated with nothing worse than `WARN`),
  1 store or command-line failure, 2 `--validate` found an `ERROR`. Unix
  `BrokenPipe` is quiet: exit 0, nothing on stderr.

## Dependencies

The standard library plus `serde_json`, `object_store` (`aws` and `http`
features only), `parquet` (no default features — no arrow, no codecs, no
async), `tokio` (a current-thread runtime, for driving `object_store`) and
`url`. That is the whole list and it should stay that way. No `zarrs`.

## Out of scope

Do not implement these without an explicit request:

- Reading array, chunk or pixel data of any kind; becoming a general Zarr
  reader or a data converter.
- Writing to a store of any kind.
- GCS, Azure, ZIP or any store beyond local, S3 and HTTP.
- Scraping HTML directory-index pages to work around a server with no WebDAV.
- Consolidation forms beyond V2 `.zmetadata` and V3 inline
  `consolidated_metadata`, or checking a snapshot against the live store.
- Validation beyond the seven rules: schema or specification conformance, a
  rule registry or policy engine, per-rule or per-severity filtering, or
  `--validate` with `--depth`.
- Parquet record, page or row-group decoding; statistics; the GeoParquet `geo`
  block; Arrow, DataFusion or Polars.
- Turning an arbitrary `.parquet` file into a tree node, or guessing the
  filenames of a payload a backend cannot list.
- AnnData beyond the table summary: values, non-zero counts, categories,
  `uns`/`layers`/`obsm`/`obsp`/`varm`/`varp`/`raw`, or H5AD/HDF5.
- async beyond the current-thread runtime `object_store` needs.

## Conventions

- Edition 2024, MSRV 1.88 (`rust-version` in `Cargo.toml`) — the floor
  `object_store`'s let-chains impose. No `rust-toolchain.toml`.
- `Cargo.lock` is committed — this package builds a binary.
- The developer is learning Rust. Explain the idiom behind a change rather
  than applying it silently, and favour straightforward standard-library
  solutions over clever or heavily generic ones.
